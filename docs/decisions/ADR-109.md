# ADR-109: Two-person adversarial review and experimental Lean authorization

- **Status:** Accepted by project owner, experimental process only
- **Decision date:** 2026-11-22
- **Selected option:** A (Decision 9)
- **Provenance:** Explicit owner selection in PWFA conversation, 2026-11-22. This is a **new** decision, not recovered historical provenance.
- **Supersedes:** [ADR-108](ADR-108.md) **only for the requirement that an independent external reviewer must authorize experimental Lean implementation**. The incremental slice model and the obligation to close every recorded *in-scope* finding remain.
- **Original constraints retained as historical evidence:** [ADR-046](ADR-046.md) and [ADR-055](ADR-055.md) are never rewritten into claims of independent approval.

## Decision context and contemporaneous choices

- **A — Two-person internal hostile review plus experimental Lean (selected; assistant-recommended):** The assistant separates design and adversarial-review roles, records all findings, remedies every in-scope finding before a prototype slice, and labels Lean output **EXPERIMENTAL / NOT INDEPENDENTLY CERTIFIED**.
- **B — Retain independent Gate 1:** External reviewer required before executable Lean; not feasible to execute within the current two-person team alone.
- **C — Experimental Lean before review closure:** Faster initial execution, but permits known unresolved defects into code and weakens provenance.
- **Other:** Not selected.

## Owner decision and amended policy

The user selected **A**. We explicitly permit **experimental Lean 4** for a bounded slice after a documented internal adversarial review and recorded closure of every finding applicable to that slice.

**Role-switching within the same assistant does not establish independence.** The review author, model, limitations and lack of outside checking must remain visible. The project must not claim that this process satisfies the originally defined independent Gate 1 or formally certifies the full PWFA mathematics.

## Mandatory per-slice protocol

1. Specify a **bounded contract**, stable file and versioned Git commit, mathematical statements and excluded scientific claims.
2. Produce an **adversarial role-separated review report** before implementing that scope; enumerate findings by stable identifiers, assumptions, counterexamples, and severity.
3. Resolve **every finding that applies to the executable slice**, including documentation findings. Document exact remediation, revision SHA and self-review outcome. Do not silently dismiss cross-slice findings: keep them open and prohibit implementation of affected scope.
4. Record an **experimental authorization** for only the remediated, frozen scope. No independent review, mathematical certification, convergence or benchmark claims arise from this approval.
5. Pin Lean and mathlib revisions. Run compile and static checks where available; record build and verification output **truthfully**. A drafted Lean file is not proof of compilation.
6. Restrict imports and public claims to the approved slice. Changes to theorem statements/axioms or cross-slice dependencies require a new review.
7. Perform a separate hostile **post-implementation check**, including checking for `sorry`, `admit`, unapproved axioms and mathematical mismatches. Formal proofs and model validation remain distinct.
8. Before **independent or production-level certification**, arrange external checking or an explicitly distinguished full-system audit. A role-separated self-review cannot be retroactively relabeled independent.

## Immediate application: SLICE-001

The [internal review](../verification/slices/spatial-phase-foundation-internal-review.md) identified a metric mismatch and undefined quotient proof obligations. Those findings remain **OPEN** for metric formalization.

The first *eligible* executable subset is **SLICE-001-PHASE**: algebraic unit-modulus complex phase properties only. It may be experimentally implemented after all applicable internal findings close, with no geometry, winding, oscillator, memory, learning or performance proof claims. The metric/geometric subset remains blocked until its findings are addressed.

## Impact and limitations

- This increases engineering feedback speed but weakens review independence relative to ADR-046/055 and ADR-108.
- Verified Lean type-checking, if obtained, establishes only accepted formal statements relative to the trusted kernel, dependencies and axioms; it does not prove that the model achieves associative recall.
- An unresolved *out-of-scope* issue must remain prominent and cannot be used implicitly by the implemented subset.
